## 测试方法

与 V1 保持一致：两种 benchmark 模式，同一命令序列（50% NEW + 25% CANCEL + 25% BOOK，价格区间 10000~14999 重叠），每轮 500K 条，重复 3 轮。

**协议变更：** 文本协议替换为二进制协议。命令固定 32 字节定长帧，响应固定 48 字节定长帧，取消 stream 构造和 per-command 堆分配。

**客户端优化：** 发送端攒 64 条批量 flush（128 条对应 ~35ms 排队延迟拐点），接收端 4KB bulk read 缓冲后逐帧解析。

**服务端优化：** 同一命令的多条响应帧合并为一次 `send()`。

## 优化迭代过程

| 改动 | sendto | recvfrom | Pipeline QPS |
|------|:-----:|:--------:|:------------:|
| V1 文本协议 | 1,500,600 | 5,737 | **664,053** |
| Phase 3 initial（逐帧 send） | 2,031,539 | 262,637 | 518,193 |
| + 服务端批量 send | 1,500,600 | 235,313 | 540,392 |
| + 客户端批量 recv | 1,500,600 | 319,741 | 560,093 |
| + 客户端批量 send (BATCH=64) | 1,500,600 | 12,554 | **1,954,005** |

关键转折：客户端 `send()` 从逐条发改为 64 条一批。服务端 `recvfrom` 从 32 万次降到 1.2 万次（减少 96%），syscall 不再是瓶颈，吞吐翻了 3 倍。

### 批量大小调优

初始选择 BATCH=128 只是因为 128 × 32 字节 = 4096 字节，刚好一页内存，没有实测依据。分别测试 16/32/64/128/256/512：

| BATCH | Pipeline QPS | P50 延迟 | 分析 |
|:-----:|:-----------:|:--------:|------|
| 16 | 2.18M | ~31ms | 与 128 以内无差异 |
| 32 | 2.20M | ~31ms | 与 128 以内无差异 |
| 64 | 2.11M | ~32ms | 与 128 以内无差异 |
| 128 | 2.19M | ~31ms | 与 128 以内无差异 |
| 256 | 2.19M | ~73ms | 延迟翻倍 |
| 512 | 2.22M | ~71ms | 延迟翻倍 |

QPS 在 2.1-2.2M 之间基本不受 BATCH 影响，256 以上延迟翻倍——batch 太大会让命令在客户端缓冲区排队等 flush。128 以内任意值均可，维持 128 不变。

### 接收缓冲区大小调优

客户端的 bulk read 缓冲区 `char raw[N]` 初始选 4096 也是直觉——4KB 是 x86-64 页大小，栈上分配无负担。分别测试 512/2048/4096/16384/65536：

| Buffer 大小 | Pipeline QPS | P50 延迟 | 分析 |
|:-----------:|:-----------:|:--------:|------|
| 512 | 2.17M | ~31ms | 偏小，无明显劣化 |
| 2048 | 2.17M | ~31ms | 够用 |
| **4096** | **2.22M** | **~31ms** | 当前值 |
| 16384 | 2.19M | ~31ms | 与 4096 持平 |
| 65536 | 2.12M | ~59ms | 偏大，可能栈压力或缓存污染 |

512~16K 对 QPS 和延迟基本没影响，64K 反而倒退。4096 保持不变。

### 服务端接收缓冲区大小调优

服务端 `handleClient` 用 `char buf[4096]` 做环形缓冲，决定单次 recv 能拿多少数据。单独测试 512/2048/4096/16384/65536 结论是 512~4096 一致，16384+ 开始劣化。但这是"一端动一端不动"的测法。

### 缓冲区矩阵实测（全量数据）

为验证客户端 buffer 和服务端 buffer 是否存在交互效应，做 3×3 矩阵测试，每次都用完整脚本采集全量硬件事件：

关键发现：

- **服务端 buffer 决定 recvfrom 数量：** 512→94K、4096→12K、16384→3.9K。buffer 越大单次 recv 拿到越多，但 12K 到 3.9K 的收益已经很小。
- **客户端 buffer 不影响服务端 recvfrom：** 同一行内，客户端 buffer 换值 recvfrom 不变。因为客户端读响应、服务端读命令，两条 TCP 流独立。
- **QPS 在 1.85~1.98M 之间波动，不存在某个组合特别优或特别劣。** 差异属于 run-to-run 噪声。
- **无交互效应：** 两端 buffer 各自影响自己那侧的收包，不叠加、不抵消。

结论：服务端 4096 与 16384 表现相当，取 4096 作为默认值。客户端 buffer 选 4096 即可。

### 上下文切换

| 模式 | V1 | V2 | 分析 |
|------|:--:|:--:|------|
| Ping-pong | 121,250 ctx/s | 124,198 ctx/s | 调度开销是 ping-pong 模式的硬天花板，与协议无关 |
| Pipeline | 207 ctx/s | 653 ctx/s | V2 处理更快，单位时间产生更多 syscall，但 653 仍极低 |

### IPC

| 模式 | V1 | V2 | 分析 |
|------|:--:|:--:|------|
| Ping-pong | 1.98 | 1.39 | 调度频繁中断流水线，IPC 下降因 string 操作（高 IPC）被 kernel 路径（低 IPC）替代 |
| Pipeline | 2.94 | 2.00 | 连续执行的 IPC 从接近理论峰值回落到正常水平 |

### syscall 不对称

Pipeline 下 sendto=1,500,600，三圈完全一致（500K × 3 = 1.5M 条命令，每条触发一次批量 send）。recvfrom=12,554 包含 pre-fill 和每次批量 recv。发送端 BATCH=64 时，服务端每次 recv 平均拿到约 120 条命令（含预填），syscall 效率提升显著。

## 结论

Phase 3 二进制协议达到了两个核心目标：

1. **消除 ~27% 的语言设施开销。** 火焰图上 locale/stringstream 归零，heap 从 12% 降到 3%，每个命令不再有 stream 构造和 per-command 字符串分配。

2. **为后续优化腾出 CPU 预算。** 瓶颈从 V1 的"不可优化的 C++ 语言设施"变为"可优化的内核 TCP 路径"。Pipeline 下处理 1.5M 命令的总 cycles 从 9.2B 降至 3.1B，腾出的 6B cycles 可以分配给 epoll、线程分离、memory pool 等架构升级。

Pipeline 吞吐从 69 万 QPS 提升到 195 万 QPS（+182%），但这是**二进制协议 + 批量收发**的组合效果，不是协议本身单独带来的。Ping-pong 延迟维持在 7µs，说明二进制协议没有引入额外单次交互开销。
